## 节点同时承载内容和层级

数据节点分为 TODO 任务和文本节点。节点的位置由父子关系确定，正文由节点自身保存，两者可以同时使用。

| 用法 | 节点表现 |
| --- | --- |
| 组织分支 | 标题作为分组或主题，包含多个子节点 |
| 记录叶子内容 | 标题、正文、标签和资源构成一条独立记录 |
| 记录中间层内容 | 节点自身记录背景、约定或结论，下方继续组织记录和 TODO |

TODO 任务与文本节点均可拥有子节点。TODO 任务另外提供进度、完成状态、优先级和排期。项目具有独立的根身份。

文本节点包含正文和子节点时，保存正文、转换类型、折叠展开和移动分支分别按自身含义执行。折叠收起后代的展示。类型转换作用于选中的节点，正文和子树随节点保存。

## Workspace 的目标定义

Workspace 保存可复用的一组执行配置。节点默认从父节点取得有效配置。TODO 任务和文本节点使用相同的 Workspace 绑定规则。

| 对象 | 保存的内容 |
| --- | --- |
| Workspace 配置 | 环境后端、连接档案、image、仓库、工作目录、优先 tmux 会话、Agent 启动命令及凭据引用 |
| 节点绑定 | 继承方式、本节点逐字段覆盖值和所选环境 ID |
| 环境实例 | 实际的主机会话、容器或 Pod，以及创建时使用的配置快照、运行状态和准备日志中的仓库提交版本 |
| Agent 会话 | 环境中的具体 Agent 实例或 tmux session／window／pane 目标 |
| 指令记录 | 来自哪个节点、投递给哪个目标、实际指令、投递状态及可用的执行回执 |

配置描述如何准备和使用环境。环境实例记录实际已经存在的执行现场。一个配置可以创建多个实例，也可以用于选择已有实例。

环境后端支持以下形态。

- SSH 主机提供工作目录和 tmux 会话。
- Docker 后端在指定主机上根据 image 创建容器，并记录容器内工作目录及会话入口。
- Kubernetes 后端使用指定集群、namespace 和 image 创建 Pod，并记录容器及会话入口。

tmux 位于环境中的会话层。主机、Docker 容器和 Pod 都可以通过 tmux 承载 Agent。仓库配置包括 GitHub 仓库地址、目标分支或版本、工作目录及凭据引用。

网页、PR 和笔记继续作为节点的相关资源。Workspace 配置中的 repository 表达环境要准备或使用的代码仓库。

## 默认继承和覆盖

节点绑定提供三种方式。

| 方式 | 行为 |
| --- | --- |
| 继承父节点 | 新节点的默认方式，沿父链读取有效配置 |
| 本节点覆盖 | 以父配置为基础，保存本节点明确设置的字段 |
| 停用 Workspace | 在当前分支建立明确的停用边界，后代可另行配置 |

覆盖字段使用「继承／设置／清除」三种意图。未写入的字段继续继承，可选字段的显式空值表达清除。每个有效字段展示来源，例如「image 继承自实验环境」「仓库分支由本节点覆盖」。

环境后端作为带类型的配置校验。切换主机、Docker 或 Kubernetes 时，按目标后端校验连接、image、namespace 和工作目录，防止混用不同后端的字段。

根节点没有上级配置时显示「尚未配置」。父配置修改后，后代的有效配置随之更新。节点移动后按新的父链解析配置。

已有环境继续关联创建或绑定时的配置快照，界面显示配置与实例之间的差异。用户可以选择现有实例，或按新的有效配置创建环境。配置继承本身只更新配置解析结果。

例如下面的树同时使用内容记录、结构组织和配置继承。

```text
Serve 项目
  Workspace = SSH 档案 + Serve 仓库 + 工作目录 + Agent 配置
  ├─ 开发约定
  │   正文 = 构建方式、目录约定、实验结论
  │   Workspace = 继承 Serve
  │   └─ 修复连接线
  │       Workspace = 继承，可覆盖仓库分支或工作目录
  └─ GPU 实验
      正文 = 实验条件和观察
      Workspace = 覆盖为容器 image 与对应运行后端
      └─ 对比实验 A
          Workspace = 继承 GPU 实验
```

`开发约定` 与 `GPU 实验` 都可以同时保存正文和组织子节点。叶子节点也可以直接配置 Workspace 并向环境中的 Agent 发指令。

## 节点详情中的操作

详情中的 Workspace 区域显示有效配置摘要、继承来源、当前环境和目标 Agent／会话。高频操作为「使用已有环境」「创建环境」和「发送指令」。配置字段在编辑面板中展开。

```text
Workspace                              继承自 Serve
SSH 主机 · 仓库 org/serve · /srv/serve

环境       dev-session                 使用已有环境 / 创建环境
Agent      codex · window @3 · pane %7

指令
[根据当前节点的要求修复连接线，并说明验证结果。]
[附带当前节点内容]                      发送
```

指令编辑器展示实际目标与将发送的内容。附带节点正文通过显式选项控制。发送时固定节点、配置快照、环境和目标会话，界面随后切换到其他节点时仍可追踪原记录。

复用 tmux 时，用户选择具体 session、window 和 pane。界面同时显示目标前台程序和工作目录。模板不指定会话；实例面板优先保留用户已选 pane，未选择时优先列出的前台程序 pane。发送时使用当时列出的 pane 进程身份。

创建环境按配置完成准备工作，并产生实例记录。容器环境包括创建运行资源、准备仓库、确定目录和启动所配置的 Agent／会话。已有环境展示 pane 的前台程序与工作目录。更换仓库或启动命令后，可按更新后的配置创建新环境。

## 投递与执行结果

tmux 投递通过准确的 pane 目标完成。多行文本按字面内容传输，提交动作由所选交互方式决定。界面明确区分「发送给 Agent」与「终端输入」，并展示实际接收程序。

服务端对节点、连接档案、配置、环境和会话逐一验证账号归属。SSH 凭据由当前账号的连接档案提供。Git／Agent 环境变量通过控制主机已有 env 文件或 Kubernetes Secret 引用，镜像拉取使用 Docker 主机凭据或 Image Pull Secret，集群使用控制主机的 kubeconfig。

每次发送具有独立指令 ID 和幂等键。相同请求的重试返回原记录。tmux 成功接收文本后显示「已投递」。目标输出可展开查看最近 200 行，指令历史保留投递状态。Agent 的实际完成情况由目标输出确认。

tmux 场景中，进程重启或连接中断可能使投递结果无法确定。此时展示「投递结果待核对」并提供目标现场，用户明确重新发送时建立新的发送记录。

环境实例分别记录准备中、可用、失败、停止等生命周期状态。创建失败保留失败阶段和日志。结束或清理环境通过环境管理动作执行。

## 持久化与兼容

节点的 workspace 绑定和可同步的配置字段进入现有 CRDT 数据模型，按字段保存覆盖意图。配置与节点内容支持导出和恢复。SSH 凭据继续保存在账号独立的服务端加密档案中。配置保存 env 文件路径或 Secret 名称。

环境实例、异步创建任务和指令投递记录由服务端保存，包含账号归属与配置快照。连接状态和终端窗口尺寸按当前设备维护。

现有 links 记录继续作为相关资源展示。已有 tmux 资源可通过「使用已关联的 tmux 配置」初始化 SSH 配置，再通过「使用已有环境」选择对应会话。原关联 ID 与会话信息继续保存在相关资源中。

新增实体与字段需要覆盖校验、CRDT 合并、备份、账号切换和旧客户端读取。跨文档保存需要明确提交顺序和失败恢复，Yjs 事务中的异常需要在写入前完成校验。

## 已实现的使用流程

1. 在任意 TODO、文本节点或项目详情中打开「Workspace 配置」，选择「本节点覆盖」。选择账号已有的控制主机 SSH 档案。
2. 选择 SSH、Docker 或 Kubernetes，按需填写 image、仓库、分支、目录、Agent 启动命令和凭据引用。保存后，后代节点按字段继承，编辑面板显示各字段来源。
3. 「使用已有环境」列出该控制主机可用的 tmux 会话、容器或 Pod。关联后选择具体 pane。「创建环境」排队准备运行资源、仓库和 tmux，会话中执行配置的 Agent 命令。
4. 输入指令，可选附带当前节点标题和正文，选择是否按 Enter 提交后发送。投递记录显示排队、投递中、已投递、失败或待核对状态。连接中断后先查看目标输出，再决定是否重新发送。
5. 创建的环境可通过确认框结束。已有环境通过「解除关联」清除当前节点的目标，之后可选择「跟随父节点环境」恢复继承。所选环境默认被后代继承，后代覆盖配置后需要选择与新配置相符的环境。

每个节点保存可选的命名 Workspace ID 和配置覆盖值。相同配置可产生多个环境和 Agent 实例。已运行的实例继续使用创建时的配置快照和连接目标，修改连接目标后需要重新关联。

## 运行依赖与持久化

SSH 主机需要预装 tmux，准备仓库时还需要 git。Docker 在所选 SSH 控制主机上执行。Kubernetes 可以通过直连 HTTPS API 使用，也兼容 SSH 控制主机上的 kubectl。容器／Pod 镜像需要 sh，缺少 tmux 或 git 时会尝试在 root 权限下通过 apt 或 apk 安装。非 root、离线或使用其他包管理器的镜像需要预装这些工具。Agent 命令依赖镜像或主机已有的可执行文件与认证配置。

Kubernetes 使用指定 namespace，Pod 为单容器，secretRef 引用同 namespace 的 Secret。创建的容器和 Pod 保留到用户主动结束。直连使用账号独立的加密连接档案；SSH 模式沿用指定 context 和控制主机 kubeconfig。

配置、环境绑定保存在 root CRDT 文档的 workspaceFields 中，支持逐字段合并、一次撤销以及 JSON／二进制备份。环境与指令记录保存在 SQLite 的 workspace_records 中，完整 data 备份包含这些记录和账号 SSH 凭据。界面列举最近更新的最多 500 个环境，从账号最近 500 条指令中提取当前节点最多 100 条，显示其中前 20 条，单独绑定的较早环境仍可按 ID 加载。

创建和发送使用持久幂等 requestId。服务重启将中断的准备或投递标记为待核对，排队操作继续处理。对相同物理环境内同一 pane 的投递顺序执行，重新确认 pane PID 与 tmux server PID 后粘贴。Pod 记录 UID，后续访问核对实例身份，删除请求携带 UID 前置条件。

Workspace 执行接口使用浏览器登录会话、现有 Origin 检查和账号归属校验，见 Swagger 的 Workspace 分组。业务 Bearer Token 的权限范围见 [API 文档](../API.md)。

## 验收

自动化回归覆盖继承链、移动节点、显式清除与停用边界、配置快照、JSON／二进制备份、独立字段合并、文本中间节点、账号隔离、幂等、重试、服务重启、多行中文投递、pane 身份变化与环境准备失败。
